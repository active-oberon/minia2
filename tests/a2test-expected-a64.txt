# Cases known to fail when the suites are compiled for AArch64 (`ob test -t a64`).
# Format: <TestFile><TAB><kind>: <case name>.  A listed case that PASSES is reported
# as FIXED and fails the run, so this file cannot silently go stale.
#
# The four entries this file shares with a2test-expected.txt are the same defects for
# the same reasons -- no procedure overloading, value parameters of non-static math
# arrays forbidden on purpose, a case with stale 32-bit assumptions, and the math array
# literal pooling bug -- and the reasoning for each is written out there rather than
# repeated here.
#
# --- also failing on x86-64, see tests/a2test-expected.txt --------------------------
MathArrays.Compilation.Test	positive: use of COMPLEX32 and COMPLEX64
MathArrays.Compilation.Test	positive: variables and parameters of math array type
MathArrays.Execution.Test	positive: correct use of ADDRESS OF and SYSTEM.VAL for tensors and open math arrays
MathArrays.Execution.Test	positive: driver tests (fill and compare arrays)
#
# --- inline assembly written for another processor ----------------------------------
# Both declare `CODE{SYSTEM.i386}` with x86 mnemonics in it. There is nothing for an
# AArch64 assembler to do with that, and it says so ("inline code is declared for a
# processor this assembler does not know") rather than reporting a parse error about a
# construct spelled as intended. They pass on x86-64, where the code is the
# architecture's own; the same two fail on ARM32 for the same reason.
Oberon.Compilation.Test	positive: call an empty inline code
Oberon.Compilation.Test	positive: export inline code with reference to (local) constant
#
# --- not in the AArch64 library ----------------------------------------------------
# The case imports JPEGEncoder, and the A64 library is the headless set
# (docker/headless-core.txt), which does not carry it. That is a scope limit of the
# library, not a defect of the target -- the same case is noted as failing in the SDK
# image for the same reason.
JPEG.Execution.Test	positive: test RGB to I420 2x2x8x8 block conversion used for encoding
#
# The three below import TextUtilities, which is not in the headless set either -- and
# unlike Texts, which a listed module drags in, nothing reaches it. Putting it in would
# put its closure in too (XML and its scanner and parser, Repositories, Configuration,
# Codecs, UnicodeProperties), and the SDK is not going to carry that so three cases can
# run. They run on x86-64, where the suites go against the whole build rather than the
# shipped subset.
Texts.Test	positive: a text counts characters, not bytes
Texts.Test	positive: inserting and deleting in the middle of a text
Texts.Test	positive: searching a text for a pattern
#
# --- written for an instruction set this one is not ---------------------------------
# The case imports Shortreal, which is AMD64.Shortreal.Mod: half precision floats
# through the AVX F16C instructions, and one of the four modules configs/moduleListA64.txt
# names as unable to exist on this architecture. AArch64 has half precision of its own
# (FEAT_FP16), so a Shortreal for it is writable; there is none, and until there is, the
# one case of this suite has nothing to import.
Shortreal.Execution.Test	positive: test scalar SHORTREAL operators

# --- the fallback logarithm ---------------------------------------------------------
# On x86 `ln` is one FYL2X instruction; everywhere else it is the series and the mantissa
# decomposition below it in Math64.Mod, and that is what AArch64 compiles. Measured against
# known values: ln(2) is 1.9E-9 out, ln(50) 9.5E-9, ln(1E6) 4.4E-7 -- growing with the
# argument, where double precision should give 1E-16. `exp` is exact to 1E-12 on the same
# machine, so this is the logarithm alone, and anything built on it inherits the error.
# The case below checks exp(ln(x)) = x to 1E-9 and therefore fails here. It is left failing
# on purpose: the number is what a math library owes, and lowering the test to fit the
# implementation would hide it.
MathFunctions.Test	positive: a logarithm and an exponent undo each other

# --- atomics under an emulator ------------------------------------------------------
# Two activities adding one to the same counter a thousand times each come to 2000 on
# x86-64 and to about 1270 here: a third of the additions are lost. The AArch64 code is
# a textbook ldaxr/stlxr retry loop and is atomic by construction on a processor, so the
# likely answer is that qemu-user does not honour the exclusive monitor between threads
# -- but "likely" is not "checked", and this entry says which of the two it is only when
# somebody runs this case on the real machine. There is one: the suites have run on a
# Snapdragon before (see the AArch64 notes), and this file should be revisited then.
# Until then the case stays here rather than being weakened to pass: an atomic operation
# that loses a third of its updates is either a defect or a broken measurement, and both
# are worth keeping in front of us.
MachineFunctions.Test	positive: two activities adding to one counter lose nothing

# --- a valid address the emulator calls bad -----------------------------------------
# The case is a client and a server over the loopback in one process. On x86-64 it
# passes. Here, under load (the suites run -j), the client's second recv comes back
# EFAULT from an address that is its own module's data, four bytes into a 64-byte
# array, with the whole range inside the one RWE segment the image is loaded from --
# measured, not assumed: the address was printed either side of the call. The first
# recv on the same buffer succeeds; adding a trace either side of the call makes the
# case pass, which is what a race looks like and not what a wrong address looks like.
# The likely answer is qemu-user's page bookkeeping racing another A2 thread that is
# growing the heap, the same shape as the atomics entry above -- and, as there, likely
# is not checked. Finding it was worth it anyway: it turned up a real defect on the way
# (Sockets.Recv decided success by a variable assigned only on failure, so a failed
# receive was handed to the caller as a length of -1), which is fixed.
Sockets.Test	positive: two ends of a connection over the loopback
