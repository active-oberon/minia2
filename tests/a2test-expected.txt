# --- UTF8Strings predates RFC 3629 -------------------------------------------------
# CodeLength still maps 0F8H..0FBH to 5-byte and 0FCH..0FDH to 6-byte forms; DecodeChar
# checks only the overlong minimum (no surrogate range, no U+10FFFF cap) and EncodeChar
# validates nothing at all. These cases demand the modern rules, so making them pass is
# an API decision — input that callers accept today would start being rejected.
Utf8Strings.Execution.Test	positive: Invalid codepoint beyond U+10FFFF (U+110000)
Utf8Strings.Execution.Test	positive: Invalid start byte 0F8X (5-byte sequence)
Utf8Strings.Execution.Test	positive: Surrogate codepoint U+D800 (high surrogate)
Utf8Strings.Execution.Test	positive: Surrogate codepoint U+DFFF (low surrogate)
Utf8Strings.Execution.Test	positive: UTF8 write invalid codepoint U+110000
Utf8Strings.Execution.Test	positive: UTF8 write invalid surrogate U+D800
#
# --- "read recovery": where does the position stand after a failed decode? ----------
# These assume a failed read leaves the position BEFORE the bad bytes and then skip them
# by hand. UTF8Strings.DecodeChar documents the opposite — "i points to the byte where
# the error was detected (this will also be the next character in the case of a minimal
# coding error)" — and for 0C0H 0AFH it does already stand on the next character, so the
# manual skip overshoots and the recovery ASSERT trips. On the contract as documented
# these tests are wrong, not the modules; the contract is the thing to settle first.
Utf8Strings.Execution.Test	positive: UTF8 read recovery after multiple invalid sequences
Utf8Strings.Execution.Test	positive: UTF8 read recovery after overlong encoding
Utf8Stream.Execution.Test	positive: UTF8 read recovery after invalid, ASCII + invalid + ASCII
